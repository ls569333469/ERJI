# 31 · ERJI 运行可观测性与导航一致性优化方案 v0.1

日期：2026-10-01  
状态：轻量阶段 A/B 已实施并完成本地验证；阶段 C/D 待后续实施

## 1. 本轮要解决的问题

买入机会页当前显示“后台覆盖 1864”，但 L1、L2、L3 都是 0。这个页面只能说明目前没有通过参与规则的机会，不能证明后台正在持续采集、补 K 线、扫描结构和生成决策。

排查后的准确口径是：

| 指标 | 当前快照 | 准确含义 |
|---|---:|---|
| 唯一资产 | 965 | 经过身份归并后的代币数量 |
| 合格市场 | 1864 | 现货、永续、Alpha 等交易市场或交易对数量，不是代币数量 |
| 历史已就绪市场 | 1179 | 已满足最低 K 线分析历史要求 |
| 历史不足或补采中 | 685 | 仍不能完成全部周期分析 |
| 当前扫描批次 | 30 | 当前这一批处理数量，会随轮转变化，不能代表总覆盖 |
| 当前批次结构命中 | 16 | 命中基础结构，不等于可以买入 |
| 当前可执行机会 | 0 | 没有通过 L1/L2/L3 的完整参与规则 |
| 当前风险记录 | 265 | 暂停、失效、数据不足等风险状态 |
| 历史信号 | 65 | 已保存的信号历史，不是后台运行日志 |

因此，1864 只能放在“覆盖范围”里，不能单独作为“正在运行”的证据。

## 2. 已确认的产品与代码问题

### 2.1 缺少用户可见的运行证据

- `WorkerHeartbeat` 只保存每个 worker 最后一次状态，下一次更新会覆盖上一条，不能查看历史。
- `/v1/health` 已能返回 worker 状态，但顶部“实时结构研究”是静态文字，没有使用这份数据。
- `StreamEvent` 会保存底层市场、K 线和信号事件，但没有面向用户的聚合、解释、分页和保留策略，不适合直接当运行日志页面。
- 买入机会为 0 时，用户看不到系统当前处于采集、补历史、扫描、否决还是异常阶段。
- 没有逐资产处理账本，无法核对某个资产最近何时完成报价、OI、K 线和结构扫描。

### 2.2 顶部工作栏没有跟当前产品同步

| 现有名称 | 问题 | 新名称 |
|---|---|---|
| 信号总览 | 当前页面实际只显示可执行机会 | 买入机会 |
| 市场数据 | 实际是价格、OI、费率盘面雷达 | 市场雷达 |
| 数据来源 | 页面同时承担来源健康和字段覆盖 | 数据健康 |
| 参数设置 | 包含策略、来源、通知和验证配置 | 策略设置 |
| 通知 | 实际只规划 Telegram；当前未启用、无目标 | Telegram 提醒 |
| 历史 | 实际是信号与决策快照历史 | 信号历史 |

本轮实施前缺少“运行监控”入口、当前页面高亮，以及由真实后台状态驱动的全局状态；轻量阶段 A/B 已补齐这些入口与状态展示。

### 2.3 页面说明与当前实现不一致

- 设置页仍写“每批 20 个市场任务”，当前信号扫描批次实际为 25，实时快照中也可能显示其他独立批次大小。
- 设置页仍写“页面每页 25 条信号”，当前买入机会页一次最多读取 300 条。
- 通知页面虽然可以配置目标，但当前通知全局关闭，且本地没有启动 `notify` worker；顶部不能暗示提醒正在运行。
- 市场雷达 `/observations` 本次读取约 2.1 秒，略高于既定 2 秒目标；其响应包含大范围市场和 OI 变化，仍需做轻量投影。

## 3. 新的信息架构

顶部导航调整为：

`买入机会｜市场雷达｜运行监控｜数据健康｜策略设置｜Telegram 提醒｜信号历史`

各页面职责必须分开：

- **买入机会**：只显示 L1/L2/L3，不为了证明系统在工作而填入普通波动。
- **市场雷达**：显示价格、数量 OI、费率等盘面事实。
- **运行监控**：证明后台链路是否正在工作、处理到哪里、过去是否持续稳定。
- **数据健康**：显示各来源、能力、额度、过期和缺口。
- **信号历史**：保存曾经形成的交易判断和当时证据。

## 4. 运行监控页面

### 4.1 第一屏：系统现在是否正常

第一屏只显示能直接回答问题的状态：

| 显示项 | 数据来源 | 显示规则 |
|---|---|---|
| 总体状态 | 必要 worker + 数据库 + 投影 | 正常、部分异常、已停止 |
| 唯一资产 | `signal_coverage.unique_assets` | 明确写“代币”，不能与市场数混用 |
| 合格市场 | `signal_coverage.eligible_markets` | 明确写“交易市场/交易对” |
| 报价有效 | `MarketState.as_of` | 显示数量和占合格市场比例 |
| OI 有效 | `oi_as_of` 与来源状态 | 现货显示不适用，不能计为缺失 |
| K 线就绪 | 四周期历史最低要求 | 显示已就绪、补采中、失败 |
| 最近完整扫描 | `signals.last_full_scan_at` | 显示具体时间和距现在多久 |
| 当前机会 | CurrentSignal L1/L2/L3 | 0 是合法结果，同时显示否决与风险数量 |

总体状态不能再使用静态绿点。任一必要链路过期时应显示黄色或红色，并指出具体环节。

### 4.2 覆盖漏斗

用一条清晰漏斗解释 1864 最终为什么是 0：

`1864 合格市场 → 1179 历史就绪 → 本轮完成扫描 → 基础结构命中 → 生成计划 → 通过风险/执行门槛 → L1/L2/L3`

每一级都必须显示：

- 数量；
- 最近更新时间；
- 与上一级减少的主要原因；
- 点击后查看对应资产；
- “0”究竟代表没有命中、数据不足、等待轮转还是 worker 异常。

### 4.3 后台链路状态

按用户能理解的顺序展示，不直接暴露内部函数名：

1. 资产目录与身份归并；
2. 报价、OI、费率采集；
3. 1H/4H/1D/1W K 线补齐；
4. 技术结构扫描；
5. PD2 参与计划与风险否决；
6. 前端机会投影；
7. Telegram 投递。

每个环节显示最近成功、最近失败、上次处理数量、耗时、下次预计运行和当前缺口。错误只显示安全的错误类别，不展示 Key、请求头或完整上游响应。

### 4.4 逐资产处理账本

这是核验 965 个代币是否实际运行的关键页面。支持搜索、筛选和分页，每个资产显示：

- 主资产及已归并的交易市场数量；
- 最近报价时间；
- 最近 OI 时间或“无合约市场”；
- 1H/4H/1D/1W K 线最近闭合时间及历史是否足够；
- 最近结构扫描时间；
- 最近扫描结果：无结构、结构候选、风险否决、L1/L2/L3、等待补数据；
- 进入不了机会页的具体原因；
- 点击进入该资产 K 线与证据。

没有逐资产 `last_scan_at` 时不能假设它已被扫描。后端需要新增当前处理状态表，由扫描器在每个市场完成后更新。

### 4.5 运行历史

运行历史采用结构化记录，不展示终端原始日志。每条记录至少包含：

- 环节与来源；
- 开始、结束和耗时；
- 成功、部分成功、失败；
- 输入数量、成功数量、跳过数量、失败数量；
- 本轮游标或批次标识；
- 安全错误代码与简短说明。

支持按日期、环节、来源和状态筛选。默认显示最近 24 小时，允许查看 7 天、30 天和 90 天。

## 5. 后端数据设计

### 5.1 保留现有实时状态

继续使用 `WorkerHeartbeat` 表示每个 worker 的最新状态，供顶部状态和实时监控读取。

### 5.2 新增运行记录

新增 `pipeline_runs`：

- `id`、`component`、`provider`；
- `started_at`、`finished_at`、`duration_ms`；
- `status`；
- `input_count`、`success_count`、`skipped_count`、`error_count`；
- `cursor`、`details`、`error_code`。

记录真实批次完成结果，而不是每次循环都写一行。异常和状态变化立即记录；持续空闲只保存低频摘要。

### 5.3 新增逐资产处理状态

新增 `asset_processing_states`，每个主市场一行，保存最近采集、K 线、扫描、决策时间及结果。该表是当前状态，不无限增长，用于分页核查 1864 个市场。

### 5.4 长期保留策略

- 详细 `pipeline_runs` 保留 90 天；
- 错误记录保留 180 天；
- 每日聚合统计长期保留，包括处理总量、成功率、失败率和耗时分位；
- 信号快照、首报、Plan 和交易研究历史沿用现有不可变保存规则；
- 不把终端文本日志、API Key 或完整外部响应写入数据库。

这样既能长期证明系统持续运行，也不会因为逐秒心跳造成数据库无限膨胀。

## 6. API 规划

| API | 用途 |
|---|---|
| `GET /v1/operations/summary` | 总体状态、覆盖漏斗、最近完整扫描 |
| `GET /v1/operations/components` | 各后台环节当前状态 |
| `GET /v1/operations/runs` | 运行历史分页和筛选 |
| `GET /v1/operations/assets` | 逐资产处理账本 |
| `GET /v1/operations/assets/{asset_id}` | 单资产完整处理时间线 |

所有接口只读数据库，不在页面请求期间调用交易所。概要接口目标 P95 小于 300ms，资产账本和历史分页目标 P95 小于 800ms，任何页面请求硬上限仍为 2 秒。

## 7. 前端行为

- 运行监控通过 SSE 接收版本变化；断线后每 15 秒补偿读取一次。
- 页面隐藏时停止补偿读取，恢复可见时立即读取一次。
- 同一投影版本不重复刷新。
- 空闲不显示为错误；超过各环节自己的合理周期才判定延迟。
- 机会为 0 时，买入机会页增加一条简短链接：“查看后台运行与筛选漏斗”，不在机会页塞入运行日志。
- 顶部当前页必须有清晰高亮。

## 8. 市场雷达性能优化

`/observations` 当前约 2.1 秒，方案如下：

1. 新增后台预生成的轻量观察投影，不在页面请求时重新组装全部市场估值与 OI 基线；
2. 市场页默认只返回当前筛选周期需要的字段；
3. 详情、跨平台证据和其他周期按需读取；
4. 接口分页，前端首屏不一次下载 1000 多行完整对象；
5. 保留 SSE 版本触发，不增加高频轮询。

验收目标：首屏 API P95 小于 500ms，前端可交互小于 1 秒，后台外部请求频率不因页面访问而增加。

## 9. 实施顺序

### 阶段 A：口径与导航

- 修正“代币/资产/市场/交易对”口径；
- 更新顶部名称、当前页高亮和真实全局状态；
- 修正设置页过期说明；
- 通知未启用时在导航中明确显示关闭状态。

### 阶段 B：实时运行监控

- 新增概要、组件状态和覆盖漏斗 API；
- 新增运行监控页面；
- 买入机会空页面链接到运行监控。

### 阶段 C：持久化历史与资产账本

- 新增数据库迁移；
- 采集、K 线、扫描、决策和投影写入结构化批次记录；
- 建立逐资产处理状态与查询页面；
- 增加 90/180 天保留与每日长期聚合。

### 阶段 D：市场雷达提速

- 建立观察投影、分页和按需详情；
- 完成接口、浏览器和持续运行性能验收。

## 10. 验收标准

1. 买入机会为 0 时，用户能在一次点击内确认数据库、采集、K 线、扫描、决策和投影是否正常。
2. 965 个唯一资产与 1864 个市场分开显示，任何页面不再混用。
3. 能搜索任一资产并看到最近一次报价、OI、K 线和结构扫描时间，以及未进入机会页的原因。
4. 重启服务后，过去 90 天运行记录仍可查询。
5. 运行日志不包含密钥、Cookie、请求头或完整上游错误正文。
6. 总体状态由真实心跳和数据年龄计算，不能使用静态绿点。
7. Telegram 未启用时明确显示关闭，不暗示正在投递。
8. 运行监控概要 P95 小于 300ms，历史与资产分页 P95 小于 800ms，所有读取不超过 2 秒。
9. 运行记录写入不会提高外部 API 调用频率，也不会突破现有并发与限流预算。
10. 生产构建、数据库迁移、回退、90 天清理和连续 24 小时运行均通过验收后，才标记完成。

## 11. 本轮边界

截至 2026-10-01，轻量阶段 A/B 已实施：新增只读数据库的 `/v1/operations`、运行监控页、统一顶部导航，并在买入机会为 0 时显示真实覆盖与扫描进度；0 条机会时不再渲染三块空表。该实现没有新增数据库表，也不会因页面访问增加交易所请求。阶段 C 的持久化批次/逐资产账本和阶段 D 的市场雷达深度优化仍待后续实施，不能用静态示例数据冒充运行记录。
