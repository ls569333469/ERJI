## 4. 阶段一：先打通数据采集、身份与消费

这一阶段优先交付。将“有多少资产”改为能核对“哪些适用字段可用、哪些缺失、缺在哪个环节”；详细诊断集中放到既有运行记录，机会主表不增加设计说明。

### 4.1 修复成功样本与失败尝试混用

**依据：** `engine/pd2/storage.py::put` 在失败时保留旧 payload/observed_at，但将 raw_ref 指向新失败请求，并更新 received_at。

**修改要求：** 独立保存最后成功样本的值、来源时间、接收时间、原始证据指针；另存最后尝试时间、状态、错误和下次重试。旧值可以用于历史展示，但不能借重试变“新”，也不能指向不包含该值的失败响应。字段迁移兼容旧记录；无法重建旧证据的记录明确标注不可追溯。

**验收：** 成功 → 失败 → 重试 → 恢复的固定回放；核对展示值、成功时间和 RawEvent 一一对应。修改前保留反例，修改后同例通过；当前所有适用消费者复核。

### 4.2 统一采集节奏与数据可用时间

**依据：** `engine/pd2/providers.py` 与 `engine/pd2/derivatives.py` 中部分 CMC/ByKaranteli 能力存在 5分钟 TTL/消费时限，对应 30分钟甚至更长的刷新间隔。

**修改要求：** 按能力明确“实时参与依据 / 较慢背景参考 / 历史证据”三种用途，分别定义源时间、允许年龄、刷新期限、预算消耗和降级行为。真实变化较快的数据不能简单延长有效期；刷新达不到实时要求时降级为背景参考，不进入实时买入依据。按实际候选需求分配付费配额，复用全市场批量结果，取消无消费者的重复请求。

**验收：** 每种能力交付刷新—有效期—消费条件表与预算估算；模拟跨多个刷新周期，正常计划不能长期制造“刚获取就不可用”。无法满足的实时能力保留明确阻断，不用过期样本通过验收。

### 4.3 解开币安 OI、历史补数与资金费率的阻塞

**依据：** `engine/adapters/binance_universe.py` 按批收集 OI、首次历史和费率后返回；OI 数量与先前批量取得的 mark 价格可能不是同一时刻。72小时播种标记只表明取得过记录，不能证明未来端点持续完整。

**修改要求：** 用现有调度器拆分实时 OI、历史端点修复、费率刷新；成功的单币结果及时持久化。每个字段保留自己的源时间；OI 名义金额优先保留上游原值，派生金额必须记录数量、乘数、报价币、价格时刻及允许偏差，时间不合格则不伪装同窗值。费率保存已结算和预测的区别、结算周期与历史游标，重启后不集中重复拉取。

**验收：** 慢币或历史补数失败不拖住已成功市场；1H/4H/1D 数量 OI 所需端点连续可取且无向未来借值；1小时结算与8小时结算分别验证日累计，不能固定四条费率当成全天。重启前后游标和预算连续。

### 4.4 修复优先级与共享预算分配

**依据：** `engine/pd2/collection_schedule.py::due` 将 participate、trial、paused、expired 都按30秒优先级处理；旧暂停/过期项可能持续占用高优先级。30/60/300秒是目标到期周期，不是实际覆盖保证。

**修改要求：** 区分仍需持仓/事件管理的暂停项与无活动计划的历史暂停/过期项；前者保留必要跟踪，后者退出快速队列。币安现货、合约、Alpha 按共同预算进行成本调度；实时依赖、收盘补齐、普通扫描、冷历史有独立积压和公平轮转，防止高优先级或冷启动永久挤压其他任务。

**当前配置取样：** 币安 family 300 weight/分钟、最小间隔500ms；Aster 240、500ms；Gecko 20、3100ms。CMC 月预算10000、ByKaranteli 15000，配置预留10%，现有预算模块另有分级降载。仅记录本地配置，不宣称这是交易所官方上限。取样上游 reported weight 曾高于本地 cap，需要核对同 IP 其他进程与账户用量，不能只算当前进程。

**验收：** 提交每类请求的实际 weight/credit、数量、频率和重试成本表，以“每分钟需求 = Σ 市场数量 × 每次权重 × 60 / 周期秒数”验证容量；月额度按供应商计费规则另算。预算不足先调整重复工作和优先级，保留退避与余量；不提高本次既有预算，不以无429作为容量充分证明。

### 4.5 打通身份、市值与 OI 比例

**依据：** Binance 合约563个市场仅74个在本次口径下有 CMC 核验映射及市值；`identity.py` 与 wallet 来源存在 Solana `501` / `CT_501` 表达不一致的静态风险，需补固定样例复现。

**修改要求：** 统一链别名及合约地址规范；Solana 地址保持大小写，EVM 按明确规则规范化。CEX 资产使用可审计的官方标识映射，不能只靠 ticker。同名、迁移、包装资产、1000数量乘数分别验证。补充来源精确地址轮转不能代替 CEX 身份映射。

OI/市值分子默认明确币安合约范围；辅助交易所单独标识，经身份与单位核验才允许合计。分母为流通市值，保存流通量、价格或供应商原值、时刻及来源；FDV 不顶替流通市值。美元换算不可用时保留原生 OI 与资金费率，不让一项缺失把所有合约信息清空。

**验收：** 输出逐资产映射覆盖表、不能匹配的原因及待补证据；抽查同名反例、现货关联主合约、数量乘数、跨所重复、流通/总量区别。任意显示比例均能复算，缺分母显示缺失而非0%。

### 4.6 报价、深度、K线与辅助源按用途补齐

报价采集成功不代表源报价新鲜。Alpha/Wallet 的接收时间不能替代源时间；池参考价、发现榜价格、mark 不能冒充买卖盘口。能提供合格来源则接通；当前不支持执行报价或卖出模拟的来源继续作为观察证据，记录具体阻断。

1H/4H/1D/1W 必须按各策略依赖独立补齐闭合柱和预热，不能因某模板不需要的周期缺失而全部停算。收盘后的迟到柱通过既有队列补齐，禁止直接把未闭合记录改成闭合。资金费率、CMC、辅助 OI、清算资料分别检查能力状态，不将“没有逐笔清算”当作所有价格策略的阻断。

### 4.7 数据契约与可核对结果

每个进入判断的字段至少可追溯：市场/资产身份、provider、数值、单位、源时间、成功接收时间、known_at、有效期、原始记录指针、覆盖窗口、版本，以及缺失原因。派生字段额外保留输入引用、公式/参数版本；事件引用 snapshot_id 与输入版本。源时间未知就保持未知。

| 字段 | 可用条件 | 缺失时的处理 |
| --- | --- | --- |
| 现价/执行价格 | 同市场、正确报价类型，满足原资格时限；当前代码参与报价≤15秒 | 等待新报价，不能用mark冒充可成交价格 |
| 深度/成本 | 可执行盘口及原成本规则；当前深度时限10秒 | 可保留技术命中，不能声称可按给定成本参与 |
| OHLCV/指标 | 已收盘、连续、预热足够、无未来值；每策略检查自己所需周期 | 指出缺周期或缺口，排队补数 |
| OI原值/变化 | 数量与单位准确，同窗端点匹配；当前诊断新鲜阈值6分钟、日线端点容差5分钟需对照消费者锁定 | 原值、变化分别呈现可用性；不把美元OI涨幅当作数量增仓 |
| OI/流通市值 | 身份、美元换算、时刻偏差均满足冻结口径 | 比例缺失不抹掉可用OI原值/费率；不一票否决无OI策略 |
| 资金费率 | 预测/已结算、周期、方向、时间明确 | 未知不按0费率；日累计要求覆盖完整 |
| 清算/辅助证据 | 真正的发生记录与模型图分开，时效适合用途 | 缺清算不确认发生轧空；模型分布不能当逐笔事实 |
| 目标/保护 | 来自已知结构或清楚标识的计算条件目标，规则版本可查 | ATH无历史阻力属于自然情形，不能补造；是否参与仍执行原资格规则 |

展示时间采用北京时间；日线/周线/OI窗口沿用数据源定义，不能把 UTC 日界线悄悄改成北京时间日界线。详细口径放标题提示或展开详情，主表只保留必要值与简短原因。

**阶段完成条件：** 针对配置范围输出“适用、已采到、已存储、可消费、已投影、前端可见”逐层对账，包含分母与缺项清单。可修代码缺陷应清零并有回归；外部不可得项列为未完成阻断。把所有空值写上原因，只算诊断完成，不算数据全部打通。

## 5. 阶段二：历史连续性、长历史与修订恢复

复用 `persistent_avwap.py`、`indicator_history.py`、`p33_coverage.py` 和既有覆盖任务，不重写第二套指标引擎。

1. 为每个适用策略登记历史要求：近期前高30根完整日线、多轮试探的30日特征/45日事件窗口、指标预热、OI端点、事件锚点以来基础量、ATH上市以来可比覆盖。不能全资产只下载同样短窗口就宣布足够。
2. 一次历史播种改为可验证的覆盖状态和持续缺口修复；保持限流，保存分段游标。未完整补齐只影响依赖这段数据的模块。
3. 验证事件 AVWAP 早期修订检测、从原锚点重建新版本、旧快照冻结和恢复；源记录修订后不能把新旧段混在一个结果里。
4. 验证超过20000根的分页计算、当前250000根上限、缺量/断页/重复柱/乱序恢复。超过能力上限明确不支持，不能静默截断后称完整。
5. 合约ATH仅在同市场上市以来历史完整时使用该名称；数据只有合约历史，不能写代币全市场ATH。

**验收：** 受控超长/修订用例继续保留，再补真实长历史样本，给出来源、区间、条数、连续性和输入哈希；同输入重算结果一致，重启不丢游标。上轮20040根受控结果不能代替真实长历史持续验收。

## 6. 阶段三：信号、快照与首次触发后的动态追踪

复用 `p33_runtime.py`、`p33_delivery.py`、`p33_lifecycle.py`、`p33_cases.py`、`decision.py`、`signal_projection.py`。本阶段先验数据链和绘图锚点，视觉呈现最后处理。

### 6.1 十种价格入口逐项对账

十种入口分别建立“命中/等待触发/失效/缺关键数据”矩阵，共40个基础格；每格记录已测、失败、无合格真实样本，不能靠一种箱体例子代表其他九种。

每个真实样例必须贯通：输入闭合柱 → 指标 → 策略与参数 → 已知锚点 → 事件 → 参与区/保护/目标 → 成本资格 → 快照 → API → A版行与详情。另覆盖多周期冲突、同币多模板命中、现货/主合约关联和无历史案例可匹配。

文案从真实字段生成，例如“4H收盘需高于具体价格、当前量比与要求差多少、缺哪项数据”；相同状态允许相同简短标题，不能所有币复制一段与实际条件无关的行动指示。历史案例有相似点、反证和缺口；不强制附一个案例，不输出未经校准的百分比。

### 6.2 事件要持续运行，不只是能打开详情

核对首次触发 → 等待/确认 → 参与资格变化 → 目标首次触达 → 保护调整 → 退出/过期/失效的适用分支。后台以新闭合柱或必要依赖更新驱动，前端打开与否不影响追踪。

冻结最初计划，追加当前变化；断档暂停后从正确游标恢复，不丢中间曾达标记录。同根K线同时触及目标与保护但无逐笔顺序时记录顺序不明；不能选择有利顺序。终态不复活，新结构另立事件并保留关联。

### 6.3 修复或验证快照刷新边界

重点复现“价格K线未变化，但OI/市值/费率变新”的情况：运行签名、计算任务与投影是否收到有效变更，列表与展开详情是否仍读旧证据。如果存在冻结过早或漏刷新，补依赖版本及触发；保留旧不可变快照，不能就地篡改历史。

**验收：** 每条机会沿 event_id、snapshot_id、strategy_version 贯通，字段相同且能回到输入；重启、断线、恢复后事件不重复。没有自然新事件时用真实历史数据因果回放补工程证据，同时保留“实时前瞻未验收”状态。

## 7. 阶段四：真实负载与持续运行

前端2秒目标指机会列表数据请求的 P95，不是保证每个外部供应商请求2秒内返回，也不是保证全部市场2秒刷新一次。

**已有证据，仅用于基线：** 上轮248项Python测试、TypeScript及差异检查通过；300行受控独立schema投影4并发20次P95为280.1ms，不含HTTP；真实2条机会HTTP同负载P95为774ms。均不证明真实全链路满负载已通过。

P34 执行时：

- 使用真实非空字段/快照构成固定负载，在隔离数据集测完整HTTP，分别记录首屏、翻页/筛选、详情懒加载、冷/热缓存及4并发；列明行数、响应体积、数据库耗时、P50/P95/P99和错误率。
- 同时运行正常采集、指标和投影；确认读列表不触发上游请求或全市场现场重算，重复刷新有合并/取消，慢详情不拖住主表。
- 提议连续观测至少24小时，覆盖多次1H/4H和一次日界线；周线边界另用真实归档回放，并注明是否实际跨过周界。记录字段新鲜率、到期积压、收盘至计算/投影延迟、重试、预算、进程恢复与空页原因。
- 当前执行报价/盘口保持原15秒/10秒资格限制；其他各能力的采集延迟SLO在阶段一完成容量测算后写入配置与验收表，再开始计时。不能测完才移动门槛，也不能用全市场平均掩盖活跃机会过期。

**验收：** 约定负载下列表P95≤2秒，无由本次修改引入的错误；持续观测中所声明可用的字段符合已冻结时效/覆盖标准。市场自然无合格机会时可空，但运行记录必须能区分“已正常分析未命中”“关键数据未齐”“计算/投影异常”。达不到时记录实际瓶颈继续修，不用空列表计时替代。

## 8. 阶段五：策略验证、参数来源与正式启用

P33 的“采用”表示实施与验证，不代表证明盈利。九种新价格策略的门槛代码已存在，目前未放行；因此正式列表主要仍见既有箱体并不意外，但不能把它称为十种策略均已正式上线。

### 8.1 先核对门槛依据

`engine/pd2/config.py::ValidationConfig` 当前默认200个成熟成交情景、30个资产、90天；`p33_release.py` 读取报告 sample 的 mature_fills/assets/days 并校验其它报告条件。本次在P33主文档及模板未找到这三个数字的明确需求出处。

P34 必须先形成参数出处表：原需求、研究建议、当前实现默认分别标识；明确成交情景的计数方式、同事件24H/72H是否重复、资产独立性、days表示历史跨度还是观察跨度，以及前瞻验证的实际要求。**这些默认数字不能直接解释为用户必须从今天再等90天。** 本轮不撤门槛、不降低参数；数值调整必须形成有理由的明确决策与版本。

### 8.2 完成有效性证据

按每个策略准备因果回放、样本外、失败/下架样本、成本、基线对比和前瞻观察。保留无成交/目标不足/历史不足的样本，防止只挑上涨成功币。18条历史事件档案及36个固定持有期情景可复用做案例检查，但不能充当充分的有效成交或普遍胜率证据。

发布报告绑定策略、参数、运行配置、输入与代码版本；修了计算逻辑就重新验证受影响报告。未通过的策略保持研究状态；通过者按原发布流程逐项启用并验证正式事件投影，不能只切开关不检查数据链。

**完成状态分开登记：** 工程链路完成 / 有效性验证完成 / 正式启用。某项尚无足够样本或上游无法恢复，要明确保留未完成原因及下一步，不能以“等待观察”抹掉还没修的代码问题，也不能为宣布完工放宽规则。

## 9. 阶段六：最后完善 K线展示

前五阶段先解决正确输入、结果与可运行性。图表底层数据接口与锚点一致性随前面同步验收，**颜色、标签、布局、默认视野和交互统一放在最后**。

1. 延续现有A版展开方式；价格/参与/合约数据集中同侧，依据与事件追踪方便连续阅读。保留现在怎么做、第一/日线/周线目标、1H/4H/1D/1W、OI/市值和资金费率。
2. 默认只画当前主价格策略及必要指标。箱体画真实上下沿与时间边界；前高/ATH画突破位；双底画低点和颈线；回踩画原突破位及本次承接；其他按P33既定对应表，不统一套箱体。
3. 4H结构在1D图仅是4H来源结构的投影，必须标明来源周期。尺度不足以说明结构时不误称“日线箱体”；不能拉伸短期整理来制造长期底部。
4. 增强边框/触发/保护/目标对比度，减少填充遮挡，提供简短标签和价格刻度；标签避让，远端日周目标不压扁当前K线。当前代码中的空文本、关闭标签/价格以及高透明填充需要重新审视实际效果。
5. 同一事件同一快照，图文单位和数值一致；缺锚点不画。快速切币/周期不串图，拖动缩放、历史分页、缺值断线和价格精度均需验证。
6. 使用真实样本人工复核十策略场景矩阵。上轮九类受控坐标、Fib C/三段保护、七类真实坐标证据保留，但坐标通过不能代替“正常人一眼看懂且没有误画”的视觉验收。

**验收：** 每种策略可从图上辨认结构、当前触发条件与失效位置；用户看到的文字和价格可回查同快照。保存真实市场、周期、事件、输入哈希与浏览器截图；未获得真实样本的格子不冒充完成。
