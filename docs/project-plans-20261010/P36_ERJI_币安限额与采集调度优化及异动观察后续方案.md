## 3. A 部分：先实施的限额与调度优化

### A1. 按接口范围管理90%预算

以下来自2026-10-04查询的公开交易规则与币安官方SDK。实施时再次核对并记录来源；供应商变更时仍按90%规则计算。`exchangeInfo.serverTime` 不作为本机时钟或数据新鲜度证明，时间同步使用对应时间接口或可信时钟。

| 限额范围 | 官方额度 | 90%可用预算 | 管理方式 |
| --- | --- | --- | --- |
| U本位合约 REST 权重 | 2400权重/分钟 | **2160权重/分钟** | 对适用接口累计真实参数权重 |
| 现货 REST 权重 | 6000权重/分钟 | **5400权重/分钟** | 同一限额范围的域名别名共同记账，不靠切换域名扩额度 |
| OI历史 `/futures/data/openInterestHist` | 权重0；1000次/5分钟/IP | **900次/5分钟** | 单独计请求次数；权重0不等于无限调用；同类统计接口如共享该限制，合并计数 |
| `/fapi/v1/fundingRate` 与 `/fapi/v1/fundingInfo` | 两接口共享500次/5分钟/IP | **合计450次/5分钟** | 同一共享桶，不分别各用450次 |
| 现货原始请求数 | 本次规则返回300000次/5分钟 | **270000次/5分钟** | 与权重桶同时满足；以后按实际返回更新 |
| 静态历史文件 `data.binance.vision` | 不冒充现货/合约REST权重额度 | 无凭据时不声称有2400或6000额度 | 单独有界下载队列、缓存和退避 |

订单次数限额不是行情采集预算，本项目本阶段不使用下单接口。Alpha、其他币安产品与其他交易所不能按域名后缀直接套用上述额度；只对已核实的接口族启用新预算，未核实接口保留原约束并独立归类。

### A3. 正确记账与限流反馈

1. 所有采集工作进程共享配额账本；总共使用90%，不是每个进程各自90%。记录限额范围、窗口、成本、来源版本、已发请求和在途预留。
2. 以请求实际发出附近的时刻记账。队列等待不提前耗尽一分钟预算；预算与并发槽位通过短事务/租约协调，等待网络时不持有数据库事务或空占大量连接。
3. 使用币安响应头校正同一IP、同一限额范围的已用量。保留本地未反映在响应头里的在途成本，避免重复相加；乱序返回的较小值不得冲掉同窗口较大值。只在正确窗口重置。
4. HTTP 200且权重已用量达到90%目标时，记为本地预算等待；未达目标不因旧的300阈值停顿。缺响应头时仍有本地计数，不能当作零消耗。
5. 429遵守Retry-After并记录接口、时间与原因；418按封禁期停止适用请求。不能通过换域名或高频重试绕开限制。失败请求已发出时不能一概退还额度；未发出的取消任务释放预留。
6. 本机之外的同出口IP请求可能消耗额度，响应头用于修正剩余量。10%余量降低风险，但不是绝对不会限流的保证。

### A4. 调整并发、启动间隔与任务批次

取消币安统一500毫秒启动间隔，以剩余预算、窗口重置时刻和实际请求成本决定下一次可发时间。对剩余预算做均匀节奏控制，不在窗口开始瞬间打满90%。

将全局固定4槽改为分接口族的有界并发，仍设本地HTTP总上限，防止拖垮连接池和数据库。初始并发属于实现参数，依据响应延迟、吞吐和数据库等待调整；不把一个未经测量的新固定并发数写成已证明最优，也不开放无限并发。

OI历史与资金费率按各自独立队列运行，移除固定“每轮2个币，完成后30秒”的吞吐瓶颈。有已到期任务且预算允许时持续派发，全部任务完成后才按下一到期时间休眠。保留任务去重、成功逐币确认、失败退避，单个慢请求不能阻塞一整批持久化或另一类采集。

本阶段采用用户本轮确认的币安当前OI基础60秒、异动/候选15秒、重点10秒目标（详见第10节）；其他来源与历史接口保持独立周期。先让调度兑现目标；必要的批次、并发和唤醒参数按实测调整，并在收尾记录中列出最终值。

### A5. 近期补洞优先，历史获得服务机会

建立三类工程任务：实时更新、现有分析所需近期窗口补洞、远期历史归档。这是采集队列分类，不新增前端业务阶段。

采用有权重公平调度与等待时间提升优先级：实时任务不能永久压住其他任务；近期补洞优先于远期历史；远期历史在额度和服务可用时也有最小服务机会。空闲份额允许其他队列借用，所有份额均在90%可用额度内部，不占用保留的10%。

队列等待设置可记录的期限。超期后释放票据、记录原因并按退避重新排队，不允许一个请求无期限等待，也不将尚未发出的排队超时写成交易所响应超时。

保留已经收到的行情和有效历史。启动、断线恢复或扫描发现近期缺口时，根据时间戳准确补洞；每页成功立即保存并更新游标。缺口位于“记录存在但未确认收盘”的K线时，同样重新核对。不能仅因最后一根更新了就认为窗口完整，也不能改时间戳或放宽连续性要求伪造完成。

远期文件下载与REST解耦，继续利用已有归档校验和断点逻辑，不为本次限额更新重建历史存储系统。优先满足现有策略的近期窗口，整段上市历史继续后台处理。

## 4. B 部分：异动发现与长期观察，A完成后再决定

**本部分仅整理已讨论的产品方向。暂不实施，不设定最终异动数值，不新建观察库表或修改现有信号页面。**

### B1. 拟议业务流程

全市场轻量扫描 → 异动立即建立第一步信号 → 优先补齐分析窗口 → 多周期策略匹配 → 给出等待、可参与、不追价或失效判断 → 长期观察与再次激活。

第一步信号表示真实市场异常，不等同于可以买。后续K线不足只影响进一步分析，不应抹去已经验证的异动；第一步自身依赖的数据仍必须真实、及时、同口径。

### B2. 拟议异动入口

| 入口 | 拟观察数据 | 仍待确定 |
| --- | --- | --- |
| 价格加速 | 短周期涨跌幅、相对近期波动的异常程度 | 窗口、方向、绝对与相对门槛 |
| 成交额异常 | 相对自身基准的放大量＋绝对成交额 | 基准算法、最低成交额、现货合约区分 |
| OI异常 | 同市场、同单位的持仓数量变化，结合量价 | 全市场轮询范围、变化窗口和阈值 |
| 接近结构或回踩区 | 上次分析确认的位置与最新量价变化 | 哪些已有结构可复用、距离与触发规则 |

拟采用满足任一有效入口即可观察，不要求价格、OI、市值、费率全部齐全。曾讨论“5分钟涨3%、15分钟涨5%、放量3倍、OI15分钟涨5%”等数字仅是候选研究参数，未定稿，不直接写进代码。验证时同时看上涨、失败和普通样本，避免只挑事后大涨的币。

### B3. 观察库与长期档案

全市场发现层保持广覆盖；高频深度观察层可集中在几十个币，但容量尚未确定。档案数量不等于高频名额：长期档案保留，沉寂后降频，再次异常恢复重点观察。必须留有新币入口，不能重现“有候选才订阅、有数据才能成候选”的循环。

币种观察档案包含多个异动事件，单个事件可以关联不同阶段的交易计划。首次时间、价格和原因冻结；持续更新最大有利变化、最大不利变化、量价/OI变化与重要转折。重复触发增强同一事件，明确去重与重新激活规则。单次计划失效不等于停止观察该币。

用户关注和活跃计划的优先级、退出/降频条件、观察容量及事件切分方式，在A完成后确定。

### B4. 数据快速反应与计划持续性

拟由全市场轻量流发现变化，候选窗口优先补齐；价格变化触发异动判断，已收盘K线触发相应策略重算，盘口变化触发当前参与条件复核。OI按真实接口周期和额度轮询，不承诺全部字段秒级。

将市场状态（启动、整理、走弱等）与数据状态（正常、补齐中、延迟）分开。将结构计划的持续有效性与即时可成交状态分开：报价过期暂停当前可买判断，观察档案和原计划不消失，数据恢复后及时复核。具体状态字段、更新架构、页面设计均留待B讨论。

## 8. A后续优先项：借鉴Hummingbot K线模块，解决采集调度阻塞

更新日期：2026-10-04。状态：已完成指定版本源码研究，工程方向可行；以下设计已随v1.3更新代码，性能仍需后续运行验证。执行顺序调整为：先完成本节数据链路改造，再讨论B异动观察；约71GB数据库的保存、清理、压缩及迁移问题另行讨论。v1.3本轮更新代码与文档，服务启动和实际吞吐验证留待下一步。

### 8.1 研究结论与证据

参考固定版本Hummingbot v2.17.0，主要文件为 candles_base.py、binance_perpetual_candles/constants.py 和 async_throttler.py。源码副本及SHA256保存在 docs/p36-research/hummingbot-v2.17.0/sources.json，避免以后主分支变化导致结论漂移。

- candles_base.py 第52–68行：使用有界deque保存指定数量的K线；默认150根，300根只是可配置示例。
- 第493–522行：首条WebSocket K线到达后启动历史填充；同一个开盘时间更新末根，新开盘时间追加新根。
- 第411–435行：计算窗口尚缺数量，通过REST向前补齐，补齐后检查时间顺序和等间隔。
- 第276–298行及563–569行：发现间隔异常会清空内存窗口；连接中断也会取消填充、清空窗口，重新建立订阅后再补。不能把它描述成已有持久化历史的精准补洞系统。
- 第54行默认每个独立feed建立限流器；第100–103行允许接入connector的共享限流器。全市场运行时必须共享适用额度，不能每个币各拥有一份完整额度。
- 合约constants.py中REQUEST_WEIGHT仍配置1200/分钟，K线权重是固定配置，不能直接替代P36已经核实的2400官方额度、90%使用规则和按limit计算的权重表。
- 内存异步锁用于协调限流，不依赖每个等待任务反复写PostgreSQL。成熟库也需要协调，但协调的范围和成本必须受控。

结论：借鉴K线生命周期与内存调度结构，适配ERJI已有数据库和策略输入；不安装整个Hummingbot交易框架，不开启交易。源码审查支持工程可行性，尚未进行ERJI性能原型对比，不能承诺秒数或以项目知名度代替实测。

### 8.2 用户可理解的目标流程

启动后先加载本地有效的最近分析窗口，同时建立实时订阅；窗口不够就下载交易所已有历史。达到实际策略需要的连续已收盘根数后即可分析，不等待整段上市历史下载完成。实时消息持续更新当前K线，断线恢复只补漏掉的区间。远期历史保持后台运行，不能挡住当前数据。

同一市场按当前已启用策略所需周期和根数建立窗口。300根不是所有策略统一上限；窗口要包含实际指标预热需求。1H、4H、1D、1W沿用现有配置；12H或其他周期只在已有配置需要时接入，不借此次采集改造新增策略周期。

### 8.3 先解决请求入口和排队，不只换K线模块

建立一个本机币安行情采集入口，由一个预算所有者统一管理适用接口的内存限流器与发送许可队列；各工作进程复用已有HTTP连接池，发出前必须向同一所有者取得并确认许可。这样无需把行情响应再通过本机HTTP代理转发一次。现有live、jobs、streams以及决策盘口请求必须梳理路由，不能在新入口之外继续独立消耗同一IP额度。

- 合约权重、现货权重与原始次数、OI历史次数、费率共享次数分别管理，仍遵守P36 A1–A2的90%规则；收到429/418按实际范围和Retry-After冷却。
- 一个采集所有者不等于一个串行请求。多个有界网络任务异步运行，空出位置就派发下一个；取消当前OI由due()默认20个币形成的批次屏障，历史衍生品每轮24个币也改为到期持续派发；已有逐币持久化必须保留。
- live/近期补洞/远期历史的优先级与防饥饿策略保留；有界队列禁止无限堆积，同一市场同一区间重复请求合并。
- 高频排队和唤醒在内存完成，不再把完整pending列表反复写回同一条数据库JSON记录。数据库只保存必要的所有者租约、恢复状态、进度和低频汇总。
- 单机多进程调用使用本机受限接口提交去重后的任务、读取结果或通知；不为此引入Kafka。客户端超时不能自动产生第二份重复请求。
- 必须只有一个有效采集所有者；租约失效则旧所有者停止发请求。重启加载仍有效的额度/封禁证据，无法确定剩余量时等待相关窗口；不靠重启清空额度。跨主机或其他应用共用出口IP时，仍按响应头校正，不能声称本机统一入口可以控制外部流量。

### 8.4 K线窗口维护的ERJI适配

以venue、market_type、native_symbol、interval、open_time作为准确身份和去重依据，现货与合约不混用。内部保留现有毫秒时间戳和Decimal精度；不能直接照搬参考实现的秒和浮点数数组。

- 启动：批量读取本地最近有效窗口并检查闭合状态、UTC周期边界和缺口；订阅启动同时允许REST补齐，不能因等待首条WS消息一直不下载历史。
- 衔接：REST下载期间继续有界接收实时消息，按开盘时间合并重叠数据。已收盘事实不能被旧的未收盘消息覆盖；保留来源与真实接收时间，不用本机当前时间伪造新鲜度。
- 补齐：近期缺口按时间范围分页，收到一页后及时入库，提交成功再推进游标；空响应、新上市不足和退市分别记录，禁止无进度的无限循环。
- 更新：同一根更新末值，新根追加；只有达到交易所闭合条件的K线进入依赖收盘的策略计算。展示中的当前K线与已收盘分析输入分开。
- 断线：保留已验证的持久化数据和有界窗口，重新连接后核对最新闭合边界，定向补洞。只有局部缓存不可信时重建相关窗口，不清空整个数据库。
- 连续性：不能用单纯根数达到300判断就绪；同时要求分析窗口连续、排序正确、收盘状态正确及最新闭合边界达到要求。周线按UTC周边界处理；不把月线当作固定30天。
- 订阅：复用已有WebSocket能力，按各产品实际连接和订阅消息限制分组；避免给每个币每个周期建立独立连接。覆盖上限和重连退避依据当前官方文档核实，不能把现货连接限制无条件套给合约。

### 8.5 OI、写入与页面响应一起检查

Hummingbot的K线窗口不解决OI过期。OI保留独立REST任务，币安当前OI改为第10节60/15/10秒刷新目标；任务按到期时间持续派发，逐币完成确认，价格证据尽量批量读取或复用可信缓存。资金费率和OI历史仍独立排队，不能与当前OI串成一个长任务。

采集与数据库写入使用有界队列分离，按有限条数或短时间窗口批量落库；队列满时产生可观测背压。历史与收盘事实不能静默丢弃，提交失败不能推进持久化游标。最新快照的合并必须保留既有数据语义和必要原始引用，不能借此修改原始事件的保留或删除政策。

页面继续读取现有投影/查询结果，不等待本轮补历史完成。排查当前机会列表2秒请求期限与实际接口延迟，减少重复查询和请求重叠；合理调整期限属于后续实现，但不能只延长超时来宣称根因已解决。不重做页面布局或策略输出。

### 8.6 实施顺序与可检查结果

1. 先做小范围可重复原型：固定一组现有币、固定周期和同样的窗口缺口，对比当前实现与统一内存调度的采集链路；新旧同时运行时不得各自占用完整额度。

3. 验证冷启动、已有部分历史、未闭合旧记录、断网重连、WS/REST乱序重叠、新上市历史不足、429/418、取消、入库失败、所有者退出与恢复。只跑模拟测试不足以证明真实吞吐。

6. 保留代码回退点和原数据。回退须关闭新入口并遵守尚有效的预算/封禁窗口；不删行情、不删原始证据、不恢复定时监控。

P0–P2是一次数据链路改造的顺序，不是新增产品发布审核。后续授权执行时，按方案连续完成必要代码检查和运行对比，统一反馈；最终产品审核由用户决定。工程检查发现缺陷应修复，不以引入人为策略审核门槛代替修复。

### 10.2 已更新代码

1. **统一内存预算。** 新增budget_owner.py，127.0.0.1:18772为本机内部许可接口，使用本机令牌；进程绑定监听端口并持有数据库所有者锁。现有HTTP连接池继续复用，所有生产入口由启动脚本设置ERJI_BUDGET_OWNER=1，统一领取发送许可、反馈和释放。不可达时失败关闭，不静默回退到另一份额度。
2. **低频检查点与恢复。** 排队只操作所有者内存；正常账本约每5秒持久化，429/418在返回前保存。失去数据库连接后停止服务；恢复先保守等待完整5分钟窗口并保留已知更长封禁，不通过重启获得额外额度。直接数据库模式只保留给隔离回归和明确回退，不允许生产中两种模式混跑。
