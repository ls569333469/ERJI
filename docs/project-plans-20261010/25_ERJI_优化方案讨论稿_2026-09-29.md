## 1. 本版直接确定的产品方向

**前端是信号看板：后台发现机会，前端显示结果。没有触发信号的币，不进入信号列表，也不随页面刷新返回。**

| 事项 | 本次确定的方案 |
|---|---|
| 主资产池 | 币安符合条件的现货、永续合约、Alpha资产全覆盖；不按成交额前200名截断。先统一身份，同币多个交易对只形成一个资产入口 |
| 辅助数据 | Aster、Hyperliquid只为主池内已确认同身份的资产补充OI、费率、清算证据；平台独有币不能自动进入主池 |
| 独立链上池 | 保留此前确定的币安钱包Meme/FOMO候选池，市值门槛按原方案；与币安池分开筛选，交集资产合并显示。辅助所目录不能代替这个池 |
| 信号总览 | 只显示已触发具体规则、尚有效的信号；统一为“建议买入”“等待买入”“风险提醒”“历史信号”；当前与历史独立查询 |
| 不再出现的占位行 | “变化小、方向未明”、无触发的普通代币、单纯数据缺失行，不进入机会列表；数据故障用顶部状态条说明 |
| 后台怎么工作 | 全池低成本扫描 → 候选提高采样频率 → 后台生成信号结果 → 前端读取结果；浏览页面不触发交易所采集或全市场计算 |
| 刷新节奏 | 前端变更推送合并为1秒一次；行情走推送；币安OI普通池5分钟、候选1分钟、活动计划30秒；完整明细见第2节 |
| 社区指标 | 11项候选及接入、画图、校验计划全部保留在第3节；本次没有“已经安装”的新声明 |

不人为凑够信号条数，也不机械限定只能显示5个或20个币。有多少符合规则就显示多少，默认每页25个；同币在总览只占一行。空列表应显示扫描覆盖、最近完成时间以及主要未入选原因统计，不用无方向代币填充。

## 2. 加载与采集：采用什么架构、多久更新

### 2.1 定下来的实现方式

采用现有PostgreSQL、后台worker和SSE扩展，**建立专供列表读取的“当前信号结果表”**。这属于正式实施项，不再写成“前面不够快才考虑缓存”。首期不引入Kafka等额外基础设施。

**数据源 → 统一资产身份 → 分层采集 → 增量计算 → 当前信号结果＋历史事件 → 页面。**

| 环节 | 后台具体做法 | 解决的问题 |
|---|---|---|
| 准入 | 先同步币安资产和钱包独立候选池，再给资产关联辅助所合约 | 不再把整个Aster/Hyperliquid目录当成机会池 |
| 基础扫描 | 所有准入资产保留廉价价格探针、闭合K线和慢速OI；无信号币不查全套盘口、不反复下载长历史 | 隐藏普通代币同时减少重计算，又能发现新机会 |
| 深度分析 | 价格/量/OI异动、接近结构触发位或已有计划时提高优先级；预算内公平轮转，记录排队超时 | 计算资源用于接近入场与需要保护的资产 |
| 信号计算 | 闭合K线只更新新增的指标值；报价/盘口变化只重评进入区与保护等受影响条件；模型和参数变更才做必要重算 | 不因一个价格跳动重算所有周期全部历史 |
| 生成结果 | worker事务写入主行摘要、行动、价位、缺失原因、有效期、版本和事件；列表最多批量核对本页最新安全状态 | 页面无需运行全市场分析，也不用等第三方API |
| 列表读取 | 后端先筛选有效信号再分页；25行目标未压缩JSON≤50KB，不返回K线数组、原始响应或重复候选；详情点击再读 | 历史审计中12行约619KB的问题从接口层解决 |
| 更新页面 | 共享SSE发送变更版本和行更新；1秒内合并高频变化，失效事件优先；断线时15秒轮询补偿，标签页隐藏时停普通轮询 | 多个页面、多位用户共享同一份结果，不增加交易所采集次数 |

当前主列表读接口目标为生产环境P95≤1秒。此目标待实施和压测验收，不代表当前已达到。后台扫描范围和前台显示数量分别统计，不能把“只显示10条”误写成“只扫描10个币”。

### 2.2 首次启动：先采集什么、每批多少

**首次没有“建议买入”等分类，先按准入规则建立监控池，再用数据产生分类。** 范围、采集批次和前端页数是三个不同概念。

| 范围 | 首次纳入标准 |
|---|---|
| 币安现货 | 正常交易的加密资产，包括只有现货没有合约的币；合并同币多个交易对，按成交额等信息选择初始参考市场，再验证执行流动性 |
| 币安永续 | 正常交易的加密资产永续，先支持已验证规格的USDT/USDC线性合约；只有合约、没有币安现货也纳入 |
| Binance Alpha | 身份、chain及CA明确，有可用行情；可信流通市值≥100万美元，并检查流动性与数据质量 |
| 钱包Meme/FOMO | 独立来源的热门/飙升候选，按原质量标准筛选；与币安资产交集去重，不用辅助所独有币替代 |
| Aster/Hyperliquid | 关联已准入资产的合约，补OI/费率等证据；它们的全目录不生成主池资格 |
| 排除及未支持项 | 停牌/退市、稳定币本身、杠杆代币和非加密资产市场默认排除。USDT/USDC作为计价币不排除；交割、反向合约等未通过规格验收的市场记录为未支持，不混算OI |

币安普通现货/永续不以市值≥100万美元或成交额前200名作为统一剔除条件；Alpha/钱包池的市值规则不能误套给所有币安资产。普通币低流动性可以继续扫描，但不等于能够通过买入执行校验。

Alpha/钱包沿用流动性总额约10万美元作为待验证初始参考，实际可买仍需检查指定金额的报价、滑点及可卖出性；供应量未知时不使用FDV冒充流通市值。新币历史不足明确标记，不凭缺周线历史删除整个币。

| 步骤 | 后台实际做什么 | 产出 |
|---|---|---|
| 1. 获取完整名单 | 读取现货/api/v3/exchangeInfo、合约/fapi/v1/exchangeInfo及Alpha独立目录；按接口实际支持能力处理USDC等规格 | 去重后的资产名单、每个资产对应的市场、合约乘数与状态 |
| 2. 获取批量行情 | 优先使用多币批量接口获取价格、24H成交额等基础信息 | 判断基础活跃度，安排初始化顺序；不等于已经产生买入信号 |
| 3. 分批补齐数据 | 每批调度20个市场/合约任务，整个REST采集队列最多4个HTTP请求并发，且受来源限频约束；已有计划保护任务可优先插入 | 历史K线、数量OI及可得历史、费率、供应量/市值、跨所关联证据 |
| 4. 逐资产初次分析 | 某资产所需数据准备好就计算对应策略，不等整批或整个池完成 | 建议买入、等待买入，或仅后台扫描；数据不足单独记录 |
| 5. 转为增量更新 | 已完成的数据不重复整段下载；按任务到期、价格变化或K线闭合事件更新 | 日常分层采集和信号追踪；中断后从已保存位置恢复 |

**20个一批不代表一个接口返回20个币的所有数据。** 币安当前OI按合约分别请求；Hyperliquid批量接口可共享读取。批内某任务失败不会阻止其余任务结果保存和分析；超时重试单独排队，不整批重做。4个并发请求也不等于每秒4次，发起速度还由接口权重与预算控制。

| 每个资产首次需要的数据 | 标准与缺失处理 |
|---|---|
| 最新价格、24H成交额、状态 | 带市场、计价币、时间与价格类型；执行价格不与标记价混用 |
| 1H/4H/1D/1W历史K线 | 首次补对应原生周期，条数按启用指标的最大回看窗口加预热要求确定，分页拉取并记录完整性；不先下载多年1H再等待聚合出周线 |
| 历史窗口与图表 | 指标登记需给出最小样本、预热长度及缺失停用条件，不能任意用统一100根宣称全部指标已就绪；目标位和图表所需更长历史可独立补数 |
| 当前与历史OI、费率 | 只对有合约资产请求；可回补则回补，否则从当前积累。缺历史不计算虚假的1H/4H/24H变化，缺OI不阻断独立纯技术策略 |
| 供应量、市值与跨所数据 | 能确认身份才归并；缺市值则OI/市值留空并说明，不能按0处理 |

首次初始化中看到的历史金叉，只用于判断当前结构；不能把历史触发时间当成系统首报时间。只有现在仍满足完整入场规则、执行数据也新鲜，才进入建议买入。

假设最终有600个唯一资产，就逐步覆盖这600个；实际市场/合约任务可能多于600，因为同一币可有现货与多个合约。每批20个任务不限制总监控数量，前端每页25行同样不限制后台范围。初始化按已有计划、收藏、新上市、活跃度等排优先级，普通资产必须有公平轮转配额。

**覆盖状态可检查：** 合格唯一资产数、关联市场数、待初始化数、已完成数、数据不足数、采集失败数、最后完整扫描时间分别统计，不把任务排队或数据缺失伪装成“无信号”。

### 2.3 首次完成后：按状态决定快慢，到期就采集

**按状态安排频率，不是按页面一个分区一个分区串行刷新。** 每个资产、来源、数据类型各有下一次采集时间；到期任务进入共享队列。同一个币同时满足多种优先级时取最紧急的一种，不重复排队。

| 页面分类／后台状态 | 币安/Aster数量OI目标间隔 | 处理方式 |
|---|---|---|
| 建议买入 | 30秒 | 检查入场判断是否有效；包括“小仓买入”和“买入条件已确认”两种入场类型 |
| 等待买入 | 60秒 | 判断是否满足指定价格/确认条件；满足后可升级为建议买入 |
| 风险提醒：仍有活动计划 | 30秒 | 不因风险降频；行情及盘口继续按各自更快通道监控保护条件 |
| 历史信号：计划已结束 | 取消该旧计划专门的高频任务 | 保存历史；资产还在池内则恢复普通扫描，新计划触发后重新提高频率 |
| 暂无信号，仅后台扫描 | 5分钟 | 维持发现能力，不向机会列表返回普通币明细 |
| 首次数据未齐或采集失败 | 独立补数/重试队列 | 不硬套买入分类；限流、故障退避，保留覆盖状态 |

例如A无信号、B等待买入、C建议买入：第30秒更新C的OI，第60秒更新B和C，第300秒A也到期。实际将同时到期的任务分批执行，不给每个币单开一个进程，也不等A采集完才轮到C。

上表针对逐合约OI，Hyperliquid继续采用批量对账与候选订阅例外；价格走实时推送，K线按新增及闭合事件计算，前端接收结果更新，不能误写成所有数据统一每30秒更新。

历史信号不高频采集不等于删除长期追踪：首报价格、升级、目标到达和失效记录均保留；仍有活动计划或新的有效信号时继续高优先级跟踪。信号分类不是必然升级路线，可以直接建议买入，也可以从等待买入失效归档。

### 2.4 拟采用的采集频率

以下是本版选择的**拟定默认频率**，不是现在线上已运行的频率。所有任务以到期时间调度、错峰执行，不能使用“一大轮全部跑完再统一睡眠”作为更新保证。

| 数据 | 普通扫描池 | 候选／有效计划 | 说明 |
|---|---|---|---|
| 币安现货/合约/Alpha资产目录 | 每30分钟同步 | 新上市/退市发现后重新校验 | 更新成员资格与交易状态，不让辅助平台补位扩池 |
| 钱包热门/飙升候选 | 每5分钟 | 活跃候选行情目标30秒一次 | 当前接口稳定性和限流需验收；若不支持频率则显示实际延迟，不承诺交易所级实时 |
| 币安成交价、报价 | 优先批量WebSocket接收 | 流内即时更新，页面最多1秒一次 | 标记价用于OI估值，成交价/盘口用于执行，不能混为同一价格 |
| 币安数量OI | 每5分钟/合约 | 候选60秒；活动计划30秒 | 只拉当前值并本地积累；1H/4H/1D滚动变化由历史快照计算；OI的1D等于滚动24H，不另建重复指标 |
| Aster数量OI | 仅匹配主池的合约，每5分钟 | 候选60秒；活动计划30秒 | 公共OI路径及权重需单独验证；遇限流按共享预算降频，明确缺口 |
| Hyperliquid数量OI/费率 | metaAndAssetCtxs每60秒批量一次/已启用perp dex | 候选/计划用activeAssetCtx订阅，入库最多15秒一次；批量REST用于对账 | 官方订阅定义确含openInterest；推送频率由源端决定，不承诺逐秒OI。HIP-3需单独注册和映射，不声称默认接口覆盖全平台 |
| 基础K线 | 缓存1H历史，每5分钟增量补末端及缺口 | 候选/计划订阅1H K线；盘中形成状态最多30秒重评一次；收盘事件立即排队 | 4H/1D/1W由同市场完整1H按交易所时区/周界聚合，定时对账原生周期；历史只在冷启动、缺口或指标窗口不足时回补 |
| 其他已启用周期 | 按自身基础粒度和闭合边界补数 | 15m/30m等策略启用时另订阅原生数据或维护1m基础 | 不能从1H逆推出15m；所需历史不齐不输出该策略 |
| 实时预测费率 | 随标记价/assetCtx推送；断线60秒REST补偿 | 同左 | 保留原始结算周期与下一结算时间；8H换算只作比较，不能冒充实际结算 |
| 已结算费率 | 每个合约结算后约60秒补一条，失败重试 | 同左 | 不再每轮拉四条历史；结算周期按平台/合约读取，不统一假定8H |
| 强平事件 | Binance/Aster公共流持续订阅，按准入资产过滤 | 有事件立即进入证据与风险判断 | 原生forceOrder是采样快照，不是全市场完整爆仓总额；HL没有在本轮核实全市场完整强平流，覆盖不足明确标记 |
| 盘口深度 | 无活动信号时不持续逐币拉盘口 | 待入场候选/计划优先订阅可重建的盘口；REST降级目标5秒 | 本地盘口必须验证快照/序列；不得用陈旧盘口继续给可买建议 |
| CMC供应量/市值补充 | 全池每6小时批量 | 候选/计划每30分钟批量 | 价格用本地原生源更新；CMC不用于逐秒价格或替代原生OI；按真实credits和账户额度预算 |
| ByKaranteli | 支持目录6小时；共享摘要10分钟 | 清算图活动币目标30分钟，其他支持币低频轮转 | 各端点真实成本、权限与覆盖决定预算；无数据标记，不用全币高频逐张地图耗完免费额度 |
| 前端列表 | 首次读取已生成的信号摘要 | 有变更推送，1秒合并；断线15秒补偿读取 | 前端刷新频率不等于源数据采集频率；显示各类数据自己的时间 |

### 2.5 免费接口与服务器资源怎么约束

以300个有合约主池资产为示例，其中30个候选、20个活动计划：币安当前OI请求约为 **250÷5＋30÷1＋20÷0.5＝120次/分钟**。每个币只属于一个优先级，不能重复计算普通池与活动池。官方SDK当前标注该接口权重1。另有300个基础1H增量每5分钟约60次/分钟；这只是示例，实际预算还须加入盘口、补数和其他服务，不能只看OI。

Hyperliquid默认perp dex的批量metaAndAssetCtxs每分钟1次，按官方“其他info请求权重20”约20权重/分钟；官方IP总预算1200/分钟。新增HIP-3 dex需要增加调用与映射预算。

每个来源设置共享的请求权重账本、并发上限、冷启动补数队列和重试退避；计划保护优先，普通扫描保留最低配额防止长期饿死。按实际exchangeInfo、响应限频头与同IP其他项目占用留余量，不把全部额度交给ERJI。429遵守Retry-After；访问限制或连接故障先报来源不可用，不靠增加并发解决。

CMC和ByK按账户实际剩余额度扣账、至少保留10%额度；月底预算紧张先降低低优先级补充频率。30分钟是目标频率，不是免费额度内所有币所有图都能同时达到的保证；每条显示实际数据年龄。现有配置的预算上限不等于已核实的账户余额。

### 2.6 不让“加载快”变成“旧建议还在推荐”

每条结果保留行情时间、OI时间、最后计算时间和valid_until。候选进入“建议买入”仍执行现有报价≤15秒、盘口≤10秒的有效性门槛；超期自动从建议买入视图移走，已跟踪计划则保留并标记暂停入场。辅助OI不可用只停用依赖该证据的策略，不误杀无需OI的纯技术策略。

后台结果采用版本原子更新；SSE携带游标，重连补事件或重新取快照。失效、撤销和保护触发不能等下一次慢速全量刷新。浏览器按有效期本地撤销可操作状态，即使推送断线也不保留旧“建议买入”。

### 4.1 技术阶段、合约证据、买入行动分别表达

市场来源与分析路径是两回事：币安/链上说明资产来自哪里；有没有可用合约决定是否增加OI分析。链上代币也可能有永续合约，不能全部当成无合约。

| 分析层 | 无合约资产 | 有合约资产 | 如何影响行动 |
|---|---|---|---|
| 技术结构 | 用价格、成交量、波动、支撑阻力和多周期状态分析 | 使用同样的技术结构分析 | 确定触发价、买入区、结构失效和目标依据 |
| 合约证据 | 显示“不适用”，不填0、不扣成弱信号 | 增加数量OI、金额OI、占市值比、跨所份额、费率及可得清算证据 | 判断持仓扩张、拥挤、空头压力、去杠杆等；不能单独把高OI当买入 |
| 当前行动 | 技术策略与可交易性通过也可建议买入 | 技术路径或明确的合约组合策略触发后，再校验执行条件 | 最终统一输出四个主分类，而不是让用户自己解读指标词条 |

技术阶段采用“区间整理、早期转强、突破确认、上涨延续、结构转弱/失效”等可解释描述方向，具体命名与阈值仍需验证。阶段旁必须标明是什么结构、哪个周期、关键价格及当前行动。例如“4H箱体已突破，但现价高于买入区，等待回踩”，不能只有“结构确认”四个字。

合约证据作为独立层，区分：价格与数量OI同时增加、空头承压候选、已观察到空头清算、清算后继续承接或走弱。空头承压需综合持续费率、仓位变化、价格位置和实际成交；已清算须有对应来源事件，清算缺失不等于没有清算，价格上涨也不自动证明发生轧空。准确触发组合与阈值仍属策略验证项。

### 4.2 “上涨增仓”必须解释清楚

**上涨增仓＝同一时间窗口价格上涨，同时可比的未平仓合约数量净增加；不要求两个涨幅相同。**

在线性合约、标的单位与汇率一致的简化例子中：原价格1美元、数量OI为100万枚，名义金额为100万美元。

| 后来发生什么 | 数量OI变化 | 名义金额OI变化 | 可以得出的结论 |
|---|---|---|---|
| 价格到1.50美元，数量仍100万枚 | 0% | +50% | 金额增长由涨价导致，不叫数量增仓 |
| 价格到1.50美元，数量到120万枚 | +20% | +80% | 价格上涨伴随数量净增仓，不是OI也必须涨50% |

简化关系：金额OI变化＝(1＋价格变化)×(1＋数量OI变化)−1。实际系统还须处理合约乘数、汇率、市场范围及采样时间一致性。

数量OI净增加表示新增未平仓合约超过减少的合约，反映多空对手双方的净新增合约敞口；不是单独新增多头数量，也不是资金净流入金额。即使OI不变，也可能同时有人开仓、有人平仓，不能据此说没人入场。

**OI周期沿用原约定：1D就是滚动24H，只显示一次；1H、4H使用相应滚动窗口。** 日线K线的1D则是按交易所日界闭合的一根日K，二者不要混淆。v0.2曾将OI的1D描述为闭合日变化，本版纠正；如将来增加自然日OI比较，应另起名称，不替换现有1D。历史端点、覆盖或单位不可比时不显示虚假的增长率。

### 4.3 多周期、提前进入与目标点位

1. 1D/1W判断大方向、所处位置和远目标资格；1H/4H寻找当前进入时机。2H及其他已登记周期可配置，但必须有足够历史并独立验收，不限于一个“金叉”指标。
2. 多周期方向一致时，早期策略可以在小周期触发后给“小仓买入”；形成中的金叉必须有独立的价格、量能及失效规则，不能仅靠“快金叉”直接买入。
3. 日线转强、周线未确认可以按适用策略提前进入；周线仍弱且只有小周期反弹时，明确按短线反弹或反转尝试管理，不能把周线远目标当已确认。若无独立反向环境策略，保留等待买入。
4. “超级底部”不能只根据跌幅大或距ATH远认定；需止跌结构、关键位、量能及可执行性证据。距ATH可作参考距离，不当作本轮必达目标或涨幅概率。
5. 买入区与保护位来自已确认结构、真实支撑阻力及经过验证的方法；日/周目标分别说明依据与触发条件，不能说1H金叉固定涨20%、周线金叉固定涨几倍。
6. 支撑阻力、箱体、均线、AVWAP、斐波那契及当前计划要实际画在K线上，曲线/锚点/触发时间与列表使用同一份数据快照；没有画出来不能算交付。具体社区方案见第3节。

### 4.4 长期追踪与清晰排版

长期首报不被升级、刷新、换页或重启改写；当前轮计划单独有进入、目标、保护与结束状态。第一目标到达后继续跟踪是否承接、突破和上移保护，不机械停止；失效旧计划不能通过切周期复活，新结构建立新计划并关联长期记录。

列表采用清晰主行和必要的次行，不强制挤成一行。主行优先显示行动、代币、现价、买入区、目标和保护；次行解释具体结构、周期及2–3条证据。OI金额/数量变化/占市值比、首报价格和时间保留可读位置，详细多平台数据、完整指标与历史按需展开。

收藏、明确跟踪的持仓保护或活动计划、接近关键位的资产保留优先级；收藏本身不等于建议买入，也不凭空推定用户真实持仓。高频任务优先不能挤掉普通资产的最低扫描配额。

|---|---|---|
| 建议买入 | 当前满足某套入场规则、计划有效、现价在买入区，执行及风险校验通过 | 现在可以按计划买入；给出买入区、目标、保护/退出条件和依据 |
| 等待买入 | 已发现明确候选信号，但现在尚不适合买入 | 明确等哪个价格或条件，例如等突破、等回踩、等收盘确认；不能只写“关注” |
| 风险提醒 | 已跟踪信号出现过期、反向证据、失效或保护触发 | 明确说明停止买入、按计划减仓或退出；来源暂时断流只说明暂停新入场，不凭断流断言应清仓 |
| 历史信号 | 此前正式触发但当前计划已结束 | 独立分页，保留首报、历次状态变化、目标到达及最终结果 |

建议买入内部保留两种直白的入场类型，不另建两个列表：

- **小仓买入：** 独立的提前进入策略已触发，具备可执行买入区、保护和目标；上涨已有启动迹象，但大周期尚未完全确认，说明未确认项和退出条件。
- **买入条件已确认：** 设定的确认规则已满足，现价仍在买入区；不代表上涨保证，也不自动意味着满仓或加杠杆。

“小仓买入”和“买入条件已确认”是两种策略入口，不是必然升级的信号强度等级；保留后台early/confirmed策略与风险参数的区别，但不重复显示同一币。

每条信号按照 **现在怎么做 → 什么价格买 → 看到哪里 → 跌到哪里退出 → 为什么这样判断** 展示。至少给：当前行动及入场类型、现价/买入区、目标位及涨幅和成立条件、原始失效价/当前保护价、关键理由与周期、首次信号价格与时间、数据更新时间；已采到的OI变化与占市值比作为资金证据展示，缺失明确说明。

建议减仓/退出必须对应原计划规则，并区分价格触达与收盘确认。未接入真实账户时是交易计划建议，不声称用户已经买入或系统已成交。目标优先来自真实支撑阻力和结构，多周期外推条件分开列，不能给指标名称绑定固定上涨百分比。

**无触发的币不进入主看板。** 单独“上涨伴随增仓”是证据，不自动等于建议买入。“结构待突破”若只是普通币还没涨，不展示；满足明确候选规则、有触发价与截止条件才进入等待买入。“结构确认”后若价格已经涨远，仍可处于等待买入。

截图中的154是当时的分组数量，不是CPU消耗占比，不能直接推算节省多少资源。低变化币保留后台廉价扫描，取消无价值明细、长历史重复拉取和盘口深扫。现有mixed以“价格或OI任一变化小于0.5%”归组，不能直接整组停采；价格异动与OI异动分别检测。持续追踪的活动计划不因短时低波动被删除。价格明显变化而OI平稳记为价格异动，OI明显变化而价格平稳记为持仓异动；只有满足明确候选规则才显示到等待买入，不把所有异动自动变成买入建议。0.5%只是旧描述阈值，后续需按周期验证。

早先“低变化N＋展开查看”的建议由最新要求调整：机会页不展示低变化明细；覆盖/搜索工具可按需查到这些资产，但不随机会页下载。缺数据、过期与真正双低变化独立记录。分组变化需防抖；正式失效与保护事件立即处理，恢复数据本身不重复首报或通知。

同一币总览只保留一个主行，显示主计划行动并展开其他策略证据；当前信号与历史计划分别存储，分页和计数采用相同身份及筛选口径。

## 6. 币安主池与去重：不是加一个开关

已检查的当前源码里存在按asset_id分组，但多数辅助所资产ID带平台前缀；同时list_markets对非币安市场基本直接允许入池。所以问题是**准入规则和资产身份没有闭合**，不是“所有去重都没有写”。

| 层次 | 必须实施的规则 |
|---|---|
| 资产准入 | 独立保存成员资格及来源：binance_spot/perp/alpha、wallet_candidate；辅助所只有数据提供者身份，不产生主池资格 |
| 资产身份 | 使用经过验证的canonical_asset_id；链上用chain_id＋合约地址，交易所资产用已审核映射。只因ticker相同不能合并 |
| 合约规格 | 1000PEPE、PEPE等必须核对合约标的与乘数后再换算；不靠删1000或平台前缀猜测同币 |
| 平台OI | 保留venue＋instrument唯一性；数量统一标的单位，金额统一USD并对齐时间；跨平台变化只用两端都存在的相同覆盖集合 |
| OI合并口径 | 展示币安OI、辅助所OI、已覆盖合计和占流通市值比；不是“全网OI”。CMC等若已含这些合约，不再与原生重复累加 |
| 单行呈现 | 每个canonical_asset_id只有一条主行；跨所证据展开看，主图与执行市场明确。当前行动来自选定主计划，其余策略作为同币证据 |
| 事件去重 | 按来源事件ID或稳定指纹幂等入库；首次触发/状态升级才产生新通知，单纯刷新价格不反复首报 |
| 历史迁移 | 先生成旧ID→新ID映射审查表，保留首报与原市场；同币多Plan不直接删除，指定主Plan并保留其他历史 |

例如PEPE在币安与Aster均有合约，主列表只显示PEPE一行，详情展示两所OI和费率；如果某币只在Aster上线，且不属于独立钱包候选池，则不能因Aster接口返回它就入选。即使它因钱包池独立入选，资格也来自钱包池，不来自Aster。

Binance采集失败时保留最后一次已验证的成员快照并提示年龄；不能改成用Aster/Hyperliquid所有币补满列表。替代价格/K线如需启用，必须显式标明参考市场与策略适用性，不能悄悄换图、换价继续发布原币安计划。

## 8. 实施顺序与验收边界

1. 先修主池资格与跨平台身份，生成迁移核对表；检查辅助所独有币不再进入主池、同币不重复、首报没有丢失。
2. 建当前信号摘要与事件读取接口，服务器过滤和分页；取消隐藏视图请求与重复响应，独立加载历史和详情。
3. 按第2节拆分采集优先级与增量计算；补来源共享预算、超时隔离、重连恢复、队列延迟及数据年龄监控。
4. 对齐“建议买入/等待买入/风险提醒/历史信号”的正式触发与失效规则，再按第3节逐项落实指标与图表；社区脚本不能靠下载图表库自动生效。
5. 用同规模数据与并发压测并记录P95；同时回放断流、去重、失效、重连、同币跨所、新上市、冷启动补数，验收后才部署。

验收必须同时通过：列表只返回有正式事件的信号；分页不重算全池；25条摘要≤50KB目标、缓存摘要读取P95≤1秒目标；无方向币仍能通过后台扫描升级为新候选；首次无分类资产仍被初始化，分批失败不阻塞其他币，合格资产无前200名截断；活动计划断流能及时暂停；页数/在线用户增加不会倍增交易所请求；辅助平台不扩大主池；OI统计覆盖与数据年龄真实可见。

**旧口径处理：** P1中的150–200资产扫描配额不再作为币安主池总量上限；本版采用合格资产全覆盖。现有配置asset_limit=200仅描述旧实现的单轮市场任务上限，deep_asset_limit=80也不等于全池只有80个币；新的批次20、并发4与显示25行分别是不同参数。P1/PD2原文保留作为历史基线，与本版冲突的上述范围和分类按最新讨论执行。

拟定性能目标、采集频率与展示规则已具体化。策略阈值、提前入场参数和目标位算法仍需按之前讨论验证，不为填满推荐页降低条件或伪造上涨概率。
