# 30 ERJI 信号链路性能与产出修复方案 v0.2

日期：2026-09-30。本文在《25 ERJI 优化方案讨论稿》和《26 ERJI 优化实施与验收记录》基础上修订。当前只更新本地方案和代码，不修改服务器。本地权威源码仍为 `D:\Axiangmu\erji\work\production-fix-20260929\src`。

## 1. 结论

现有实现没有完整达到25号方案的目标。

已经完成的是输出层优化：普通波动和方向未明资产不进入信号页；页面只读取 `current_signals` 摘要并分页显示25条。

没有完成的是计算层优化：后台仍周期性扫描大量市场和K线，投影任务仍反复重建结果，覆盖统计仍在信号发布事务中遍历K线；这些任务与信号接口共享数据库资源。前端少显示记录，并没有让后台少读K线、少计算或少争用数据库。

因此，当前问题不是“前端行数太多”，而是信号产生链路没有真正增量化。26号记录中的“事件触发、5分钟全池兜底、后台预生成”只能视为代码路径已建立，不能视为生产性能已经验收。

## 3. HTTP 451 的正确边界

HTTP 451 不是本次现货等待信号消失或页面缓慢的直接原因。

- 服务器访问 Binance USD-M Futures `fapi.binance.com` 返回451，影响服务器上的币安合约目录、OI、费率、合约K线和合约盘口。
- 服务器的 Binance Spot 已通过 `data-api.binance.vision` 更新；核查时754个现货市场中大部分报价可保持新鲜。
- 本机按ERJI实际使用的Python系统代理路径测试，Binance Futures `time`、BTC `openInterest` 和 `klines` 均返回HTTP 200。
- 本机不走代理的 `curl` 是连接超时，不是451。因此本地采集必须明确记录所用网络路径和代理状态。

结论：服务器451作为“合约来源缺口”单独显示；现货技术信号照常计算；本地开发与验收不再把451当成信号页性能问题的解释。

## 4. 修复后的链路

### 4.1 四级处理，不对全池做同样重的计算

| 层级 | 资产范围 | 后台工作 | 产出 |
|---|---|---|---|
| L0 目录层 | 全部准入资产 | 目录、状态、基础行情和历史完整性水位 | 是否进入基础扫描 |
| L1 轻筛层 | 历史已齐资产 | 仅在新闭合K线到达时更新EMA、MACD、成交量、箱体候选等增量特征 | 无信号或候选 |
| L2 候选层 | 接近触发、结构有效或多周期转强资产 | 完整1H/4H/1D/1W评估、目标和失效条件；有合约时补充OI/费率 | 等待买入 |
| L3 执行层 | 已触发且接近参与区资产 | 15秒报价、10秒盘口、费用、滑点、盈亏比和账户风险校验 | 建议买入或明确否决原因 |

普通资产保留发现能力，但不反复执行目标计算、跨市场OI聚合、盘口请求和完整Plan重建。Aster、Hyperliquid继续只作为已匹配主池资产的补充证据，不独立扩充主池。

### 4.2 技术扫描改为事件驱动和分片校验

1. K线闭合事件只把受影响的 `instrument_id + resolution` 放入扫描队列。
2. 扫描器只读取该市场所需窗口，不再为一次事件读取全池最近300根K线。
3. 每个市场保存 `last_scanned_candle_close`、规则版本和特征版本；同一闭合K线不重复计算。
4. 原“每5分钟全池兜底”改为游标分片校验，例如每批25至50个市场，持续轮转；它负责发现漏事件，不同步阻塞全池。
5. 冷启动补历史和实时扫描分队列。补数慢不能阻塞已有数据资产的信号更新。
6. 为闭合K线读取增加或核实局部索引：`(instrument_id, resolution, open_time DESC) WHERE is_closed = true`；用 `EXPLAIN (ANALYZE, BUFFERS)` 验证实际命中后再保留。

### 4.3 投影不再每2秒全量重建

当前 `decision_list()` 每2秒遍历当前Episode/Plan/Snapshot并重新发布；覆盖统计还会周期性聚合全体K线。修复为：

- Episode、Plan、Snapshot或市场安全状态变化时，只更新对应资产的 `current_signals` 行。
- 资产失效、退市或身份变化时，通过明确事件删除或暂停对应投影，不靠全量重建发现。
- coverage统计移动到独立低优先级任务，建议5分钟一次；结果写入独立健康摘要，不占用信号发布事务。
- 投影心跳分别记录事件积压、最后成功事件、处理耗时P50/P95和失败数。

### 4.4 信号接口只读，避免页面请求写数据库

当前列表读取会创建分页快照记录。后续改为使用投影版本号和游标分页，GET请求不写数据库。

- 查询只访问小型 `current_signals` 与对应最新报价；不访问原始K线、OI历史或技术计算表。
- 预先维护分类计数，避免每次请求重复做窗口排序和全量count。
- 增加并验证 `current_signals(action, computed_at DESC)` 等实际查询所需索引。
- API和重型worker使用独立连接池上限；扫描任务不能耗尽页面读取连接。
- 可增加1至3秒进程内只读缓存，缓存键包含分类、搜索、排序、页码和投影版本；安全判断仍按最新报价及有效期执行。

### 4.5 分离四种时间，修正等待信号消失

不能继续用一个 `decision_as_of` 同时判断所有分类。

| 时间 | 用途 | 建议有效规则 |
|---|---|---|
| `quote_as_of` | 当前展示价格 | 页面显示年龄；等待信号可容忍分钟级，但必须明确标记 |
| `structure_as_of` | 最近一次结构评估所依据的闭合K线 | 有效到下一根相关K线应闭合的时间加宽限，不使用固定6分钟 |
| `execution_as_of` | 买入所用报价和盘口 | 建议买入继续严格执行报价15秒、盘口10秒 |
| `projection_as_of` | 摘要行最后更新 | 用于监控后台是否积压，不直接证明结构失效 |

等待买入只有在结构失效、所需K线超过周期宽限、资产退出主池或关键数据缺失时转为风险。价格持续更新而闭合K线尚未变化，不应让有效箱体因为6分钟过去而从等待列表消失。

## 5. 前端显示与性能

前端继续只显示有意义的四类结果，不恢复普通波动行。页面需要把“数据慢”说清楚，而不是表现为空列表：

- 首屏先返回信号行和分类计数，coverage等较慢统计异步加载。
- 显示“最新报价”“最新结构评估”“后台队列延迟”三个独立时间。
- 等待买入为空时，区分“确实没有候选”“候选结构已过期”“扫描积压”“历史未就绪”。
- SSE只在投影版本变化时刷新；断线15秒补偿保留，但同一版本不重复请求。
- 前端不负责技术分析，也不通过降低门槛制造买入记录。

## 6. 实施顺序

### P0：先修正确性和页面可用性

1. 拆分四种时间，修复等待结构被6分钟统一门槛错误转入风险。
2. 将coverage全表统计移出信号发布事务。
3. 增加扫描耗时、读取K线数、队列深度和投影年龄监控。
4. 给空列表返回可核对的排除原因统计。

### P1：消除主要性能瓶颈

1. 全池同步扫描改为事件队列加游标分片校验。
2. 投影改为按资产增量更新，停止每2秒全量重建。
3. 信号GET改为纯只读；核实索引和连接池隔离。
4. 冷启动补数与实时扫描分离，候选和活动计划拥有独立高优先级队列。

### P2：补齐信号产出能力

在性能链路稳定后，把已约定的方法落实为独立、可验证的候选入口：多周期趋势共振、EMA/MACD动能、箱体突破、支撑阻力回收、布林收缩后扩张、成交量确认，以及有合约资产的OI/费率/清算证据。每个入口都必须有触发、反证、参与区、保护和目标依据，不能仅输出指标名称。

## 7. 验收标准

以下项目必须在与目标资产规模接近的本地环境连续运行后验收，不能再用1,000条静态模拟记录代替：

| 项目 | 通过标准 |
|---|---|
| 信号接口 | worker运行和采集并发时，`/v1/signals` P95小于500ms、P99小于1s，连续30分钟无超过3s请求 |
| 事件延迟 | 闭合K线入库到对应等待信号更新P95小于10s；活动计划报价/盘口更新到撤销可买状态小于3s |
| 等待信号正确性 | 报价更新但未到下一根闭合K线时，等待结构不因固定6分钟超时消失 |
| 扫描公平性 | 全部历史就绪主池资产在设定轮转窗口内完成校验；不只反复扫描少数币 |
| 数据库负载 | 常态无持续30s以上K线扫描；记录慢查询、读取块数和命中索引 |
| 资源 | worker无OOM和异常重启；内存、连接数和队列积压在连续运行中有上限告警 |
| 分类可解释 | 建议买入、等待买入、风险提醒为空或有数据时，都能给出按原因聚合的数量 |
| 本地合约源 | 使用项目实际Python网络路径，目录、OI、费率、K线连续采集并记录数据年龄；HTTP 200短测不替代连续验收 |

### 9.1 已实施

- 全池结构扫描改为持久游标分片，每5秒从数据库校验25个市场；K线闭合事件继续优先处理对应市场。
- 基础扫描仅读取1H/4H最近120根闭合K线，只有形成候选后才读取1D/1W目标所需数据。
- 等待买入使用 `structure_as_of` 和 `structure_valid_until`，不再因统一6分钟决策年龄被错误隐藏。
- coverage改为独立5分钟低优先级心跳；信号投影改为事件触发并保留30秒兜底，过滤投影自身事件，避免循环重建。
- `/v1/signals` GET不再写分页快照到数据库，改为进程内有限TTL缓存；新增闭合K线和信号分类索引。
- 前端信号请求硬超时为2秒；超时保留上一份结果并明确提示，页面分别显示结构扫描和投影时间。
- 本地停止脚本会递归停止已验证父进程的子进程，避免Python/Next启动器退出后端口仍被占用。

### 9.2 外部API频率规则

“数据获取不超过2秒”定义为信号页单次HTTP读取不超过2秒，不表示每个资产每2秒调用一次交易所。交易所数据由后台队列更新，页面读取本地投影。

| 来源 | 共享预算 | 最小间隔 | 说明 |
|---|---:|---:|---|
| Binance全家族 | 300内部权重/分钟 | 500ms | `data-api`、`fapi`、`www`等域名共享同一预算，避免各域名分别跑满 |
| Aster全家族 | 240内部权重/分钟 | 500ms | 响应头报告用量达到上限时退避到下一分钟 |
| Hyperliquid全家族 | 300内部权重/分钟 | 1000ms | 单次请求按20内部权重估算 |
| OKX全家族 | 120内部权重/分钟 | 500ms | 仅作为补充来源 |
| GeckoTerminal | 20内部权重/分钟 | 3100ms | 维持低频链上补充 |

所有worker共享PostgreSQL预算记录和4个跨进程HTTP槽。收到HTTP 418/429时至少退避60秒；Binance响应头报告权重达到本地上限时，也会停止到下一分钟。该预算只允许降低吞吐，不允许为了页面速度临时提高频率。
